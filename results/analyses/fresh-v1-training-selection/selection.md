# Training-data selection on `fresh-v1`

> **Post hoc, exploratory (not pre-specified).** Built from the records of `fresh-v1` after the run was graded and analysed; it never replaces the run's own analysis (`analysis.md` in the run directory). This step trains, samples and downloads no model, and nothing here measures training value. The configuration's status: A configuration of the planned data step (experiments/downstream_plan_v0.1-draft.md, section 2), applied post hoc to the recorded run fresh-v1 for the plan's illustration (section 9). The experiment has not run, and fresh-v1's attempts are not its training data; its stage 0 needs a new configuration that names the pool's run. Applying this one trains nothing, and its output is not a result of training. Labels: rule D19's proposals (labeler `builder:refcheck+regression+construction:v1`), which are model proposals; no attempt has a human label. Fresh attempts are made without any verifier, reference or label (protocol §15.4), so none was optimised against a verifier. 40 of the 79 attempts saw only the first request (variant `u1`), by the run's design, and the invalid counts below follow from that design.

Generated by `python scripts/build_training_selection.py --config configs/downstream/rft_selection_v0.1.json` (config sha256 `9666ab5b15bd`). The run: code revision `eb56aec76e3b`, each pair graded 3 times, tc-harness/0.3.5. Every input's sha256, and the selection code's, are in `selection_manifest.json`. Every selected pair's origin, outcome, label and negative type match the run's `analysis.json`, and so do its excluded attempts and the cells its oracle-gated view drops.

* **Acceptance, the run's own rule.** A condition admits an attempt when the run recorded `pass` for the pair. Each pair was graded 3 times, and the grader records `pass` only when every repeat passed: repeats that disagree are `unresolved` (protocol §6, §15.3). Every other outcome is a rejection. No pair read here is unresolved, missing, recorded twice or ended in an infrastructure outcome; the script refuses a run where one is.
* **The cell gate.** A condition contributes data from a task only when its verifier passes the task's reference (a recorded `pass`, on every repeat) and, where the run graded the task's no-op, fails on it (a recorded `task_failure`). The run graded no no-op of these tasks, so the gate here is its reference part alone, which is the analysis' oracle-gated view (protocol §15.7). The data filters are the gated sets; the ungated rows describe each verifier. Dropped cells: C1 drops CS-01 (does not pass its reference (task_failure)); C2 drops CS-01 (does not pass its reference (task_failure)).
* **Attempts.** 79 fresh attempts that the run's analysis keeps. Excluded by its rule: `CS-02-fresh-A-final-1` (the fresh-attempt audit found a read of forbidden material). Graded candidates that are not attempts, not selected: 4 `reference`.
* **Kinds of invalid attempt.** A correction violator breaks a reference requirement introduced after the first request; a regression-only attempt breaks only the regression norm (violated requirements exactly `REGRESSION`); other: any other invalid attempt.
