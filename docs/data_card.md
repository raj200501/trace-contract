## Construction pilot: held-out candidates and labels (per task)

The construction pilot grades the four families' frozen verifiers on the constructed pool
described in this section: 32 held-out candidates, of which rule D19 labels 17 invalid, 10
valid and 5 ambiguous. Its final run is `pilot-v0.3.3`. Since protocol v0.7 that run is
the record of the original pilot, its families are the development families of the
phases that follow, and its later re-analyses are post hoc and exploratory (§15.1;
`results/analyses/pilot-v0.3.3-exploratory/`, D49). The re-grade `pilot-v0.3.5-regrade`
agrees with it on all 240 pairs (D54).

Every task has the same pool:
* The pre-correction state was captured during the session, before any verifier
  existed. Its edits appear, abbreviated, in the session text that B2's generator and
  the full-session contract proposer read.
* The alternatives and near misses were generated after all of the task's evaluated
  verifiers were frozen (CS-04's B1 was re-selected afterwards; decision log D31), by
  separate agents, each exporting its own workspace directory. The agents ran as the
  same user in the repository checkout, so verifiers and registered candidates were
  readable. They were told not to read them. They also shared the build session's
  scratch directory. An audit of the tool inputs of every generator whose output was
  registered found no forbidden read. A stricter re-audit of all 21 generator and
  reference-check transcripts (decision log D44, hardened in D46) resolves the paths
  instead of matching substrings, also applies the first audit's rule and flags every
  literal forbidden path in a tool input, and treats the whole scratch directory as
  forbidden. It found no read of candidate, verifier or sealed material. The listings
  it found, and the one read of another agent's file in the scratch directory, are
  given in the exceptions below. Neither audit script reads tool outputs, and the
  re-audit script matches paths that inline code builds at run time only by name. In
  `tasks/*/labels/generator_audit.json`, the accesses the re-audit flags were assessed
  by reading the transcripts, tool outputs included; the other assessments restate the
  script's classification.

Exceptions (decision log D31, D37, D40, D41, D44):
* near-miss generators had, and ran, B1's test files (the test hunks of the reference
  diff);
* three held-out candidates duplicate a development attack used in their family's C4
  audit. `CS-04-pre-correction` and `CS-04-eval-nm-2` have the same graded patch as
  `CS-04-dev-attack-full_session-a3`. `CS-01-eval-nm-5` differs from
  `CS-01-dev-attack-full_session-a3` by one docstring line (`tasks/*/labels/duplicates.json`).
  Neither C4 audit made a revision;
* in all four families the reference checks were written while the pool was being
  generated; CS-03's were frozen before its pool was registered, and CS-02's were
  revised after its pool was complete;
* the held-out and reference-check prompts of 2026-11-18 (CS-01's near-miss prompts
  and all of CS-02's) differ from the CS-03/CS-04 prompts, which CS-01's alternatives
  and reference checks also used;
* the held-out generators, the reference-check writers and their reviewers shared the
  build session's scratch directory with the builder (the study's AI agent) and with
  each other. The first audit treated only its sealed subfolders as forbidden. The
  rest held other agents' working files and material derived from candidates (decision
  log D44, D46):
  * extracted by the builder on 2026-11-13: the patch of `CS-04-eval-alt-1`, a state of
    that candidate with two of B1's overlay test files (`b1probe/`), and the patch and
    a state of `CS-03-pre-correction`;
  * written by the independent check agents on 2026-11-18: outputs for registered
    candidates, and the patches of all eight CS-03 held-out candidates (two folders).

  No audited agent opened any of them. The re-audit found listings that showed names
  only:
  * the directory's top level, listed once each by CS-02's near-miss generator and by
    the third reviewer of CS-02's reference checks; both listings showed
    `CS-02-eval-alt-1` in a file name;
  * `tasks/<id>/verifiers/`, listed by the CS-03 and CS-04 reference-check writers;
  * the directory that holds CS-02's workspaces, listed by one fixer of CS-02's
    reference checks;
  * `git status` at the repository root, run by both fixers of CS-02's reference
    checks, whose output named CS-02's held-out candidate files (seven and two names).

  The third reviewer also listed the first reviewer's folders there and read that
  reviewer's whole test runner (16 lines, with `head -50`), which imports the four
  reference-check test modules and prints PASS or FAIL. Under the re-audit's rule this
  is a read of forbidden material; the runner is outside the read-only list in the
  reviewer's prompt and holds no candidate or other verifier material. Every other read
  in the scratch directory was of the reading agent's own files;
* the hash of each verifier's scored check list was added after the run `pilot-v0.3`.

## Fresh-agent attempts (`fresh-v1`)

A second candidate set for the same four families, graded by their frozen verifiers
(protocol §15.4, §15.5, §16.2, §18; decision log D55 to D58, D61, D62). It adds
candidates, not tasks.

* **Attempts.** 80: per family, two variants of the instruction (`u1`, `final`), two
  agent configurations (A and B) and 5 attempts per cell (k = 5). The configurations'
  model identifiers are kept in the private run records only (D56). Each attempt ran in
  its own workspace outside the repository, with a fresh git copy of the base snapshot,
  the instruction and the sandbox wrappers, and nothing from `tasks/`, `results/`,
  `docs/`, `data/` or `paper/` (§15.4). The instructions and their sha256 values were
  logged before the first attempt started (`data/fresh/fresh-v1/instructions.json`, D56).
  The attempts ran on 2026-11-21 from 08:58:21Z to 10:21:02Z (D58), and all 80 ended by
  delivering their report.
* **Candidates.** Each attempt's final state, without `.git`, caches and the files the
  patch policy excludes (the attempts' edits of test files among them), is a candidate
  with origin `fresh_attempt`, registered in the stratum manifest
  `tasks/<id>/strata/fresh-v1.json` (`tasks/<id>/strata/fresh-v1/candidates/`), so
  `task.json` is unchanged. The 80 patches are distinct. Before grading, every recorded
  patch was derived again from its workspace, and all 80 are identical to the recorded
  ones (D58).
* **Audit** (`data/fresh/fresh-v1/audit_<id>.json`, `scripts/strict_reaudit.py
  --fresh`). Every tool input and output of every attempt was scanned. The script flagged
  26 attempts, and each flag was read in its transcript. One attempt is excluded:
  CS-02-fresh-A-final-1 wrote three helper files in the build session's scratch
  directory and read them back (D62). The sensitivity view excludes all 26 flagged
  attempts (§18.1). Harness context outside the tool calls reached the attempts: a
  working-directory line naming the study repository, the build session's scratch
  directory as a place for temporary files, and reminders listing the build session's
  task titles (by the audits, in every attempt but 4 of CS-04's). It held no task
  material (§18.2, corrected in D62).
* **Labels.** Rule D19 treats each attempt as a natural candidate: invalid if any frozen
  reference check or the regression norm fails, else valid, so none is ambiguous (D58).
  The labels are in each candidate file and in
  `tasks/<id>/strata/fresh-v1/proposed_labels.json` (labeler
  `builder:refcheck+regression+construction:v1`). They are model proposals, not human
  labels. Of the 79 analysed attempts, 29 are invalid, all of them `u1` attempts, and 50
  valid. 27 of the 40 `u1` attempts violate a correction requirement; the other 2
  invalid ones (CS-02-fresh-A-u1-4 and -u1-5) fail only the regression norm, through one
  base test that asserts on a private attribute both removed (D61, D62).
* **Second labeling.** One independent labeler per family (§15.5, D55), written by
  configuration B from the reference contract and the base snapshot (with the harness
  API, the lint rules and a synthetic example of the test format), without the reference
  diff, the reference checks or any candidate, and frozen before any fresh attempt
  existed: `tasks/<id>/verifiers/independent_label/`, registered in
  `tasks/<id>/verifiers_extra.json`. The strict audit of its writers is
  `data/labelers/writer_audit.json`: CS-01, CS-02 and CS-04 independent, CS-03 with
  concerns (D58). It agrees with D19 on 77 of the 79 analysed attempts (kappa 0.94; D61).
* **Human review.** The analysis queues all 79 analysed attempts for human review
  (`results/runs/fresh-v1/analysis.json`, `labels.<id>.strata.fresh-v1.review_queue`).
  `tracecontract review-packet ... --strata fresh-v1` puts these 79 into the blinded
  packet among each task's own held-out candidates, blinded as they are, and leaves out
  the excluded CS-02-fresh-A-final-1 (`src/tracecontract/review.py`; annotation guide,
  section 2; D82). On the recorded tasks such a packet holds 110 items for 111
  candidates, because two CS-04 pilot candidates have the same diff and share an id.
  `tracecontract merge-reviews` appends the reviewers' labels to the attempts' files in
  the stratum (`tasks/<id>/strata/fresh-v1/candidates/`), whose hashes the analysis of
  `fresh-v1` records among its inputs. No human label exists yet.

## Natural PR-review tasks (`natural-pr-v1`)

The six accepted families of the first sample (NP-03, NP-04, NP-05, NP-18, NP-19 and
NP-20) were built by the recipe fixed in D64 and D65, in phases P1 to P7 (D70, D72, D75),
and graded in the run `natural-pr-v1` (D76 to D78; `results/runs/README.md`). Each phase
end is a line of `data/manifests/natural_phase_ends.jsonl` (42 lines: ids, file hashes and
freeze times), committed and pushed before the family's next phase. Every generator ran in
its own workspace, from a prompt rendered from one of the 15 templates in
`experiments/prompts/natural/` and checked against its rendering before it was sent, and
every contract, generated verifier and constructed candidate carries a generation record
(D64, D65). Every agent of the recipe is configuration A, except the independent
labeler's writer and its revision, which are configuration B (D64). Per family:

* **Contracts:** the initial-only contract (from the issue), the full-session contract
  (from the issue and the review thread), and the reference contract, drafted by its own
  agent from the rendered thread, the reference diff and the addressing diff (D64,
  deviation k); two model mappings of each recovered contract to the reference contract.
  All are model proposals.
* **Verifiers:** C1 to C4 and B2 from the controlled arm's templates, adapted (D64); B1,
  the base-test subset's tests at the addressing commit that pass on the reference (D59),
  frozen since P0 (D70); and B3, a secondary arm written from the initial request and the
  reference diff, with no contract (§15.6). C2 and C4 went through audit:v1, and five of
  the twelve audits still failed after their third revision (D70).
* **Label support:** the reference checks, usable in all six families (fix rounds: 2 in
  NP-05, 1 in NP-19, 0 in the others; D72, D75, D77), and the independent labeler, usable
  in four. NP-03's and NP-19's labelers fail on the reference and are left out of the
  second labeling (D72, D75).
* **Held-out pool:** the pre-review state (the tree the reviewer commented on, §15.6),
  two valid alternatives and three near misses. Each alternative and near miss was
  generated after the family's last freeze by its own agent in its own workspace (D72,
  D75), and each near miss was given its target requirement by the host. In every family
  two of the three near misses target a requirement introduced at the correction
  (`results/runs/natural-pr-v1/analysis.md`).
  The development candidates (two alternatives and eight attacks per family) served the
  audit loops; the run grades the held-out pool, the reference solution and the no-op.
* **Labels.** D19, with three repeats, labels the 36 held-out candidates (12
  alternatives, 18 near misses, 6 pre-review states): 11 valid (every alternative but
  one), 21 invalid (15 near misses and all six pre-review states) and 4 ambiguous, which
  are left out of false acceptance and false rejection and queued for human review (D76).
  Each pre-review state also has the source-evidence label of §15.6: invalid with respect
  to the correction, on the strength of the reviewer's request, the addressing commit and
  the agreement of both S9 judges, reported apart from D19. None of these is a human
  label, and every family's provenance awaits a human reviewer (§16.4), so the run is an
  automated pilot (D75, D76).

The construction facts per family (requirements, checks, audits) are in
`results/runs/natural-pr-v1/analysis.md`.

## What is stored in this repository

* Sanitised controlled transcripts (`data/controlled/transcripts/<id>.jsonl`):
  conversation content, tool calls/results, timestamps, entry ids (`uuid`,
  `parentUuid`), model name, stop reasons and token usage only. Harness internals and
  internal session and agent ids are removed, and every entry is relabelled with a
  study session id (decision log D9, D38). The session agent's thinking text is kept
  as recorded: 178 thinking blocks, 111 of them empty.
* Task directories (`tasks/<id>/`): manifests, provenance, snapshot manifests,
  contracts, candidate patches, verifier tests and specs.
* The fresh-agent stratum (`fresh-v1`): per family, the stratum manifest and its 20
  candidates, each with its captured patch, its attempt record and its D19 label
  (`tasks/<id>/strata/`); the instructions, the attempt records and the audit reports
  (`data/fresh/fresh-v1/`); the independent labelers
  (`tasks/<id>/verifiers/independent_label/`, `verifiers_extra.json`) and the audit of
  their writers (`data/labelers/writer_audit.json`). Each audit report identifies an
  attempt's transcript by its sha256 and keeps, for each flagged access, an excerpt of at
  most 80 characters, with session-local paths replaced.
* The runs (`results/runs/`, indexed in its README): manifests, raw results, analyses and
  HTML reports. `natural-pr-v1` publishes only its manifest, its analysis
  (`analysis.json`, `analysis.md`) and `results_public.jsonl`, whose lines hold ids,
  outcomes, rewards, counts of checks by status and hashes, with no check id, message or
  diagnostic (D78).
* Natural-data screening records (`data/manifests/`): ids, commit SHAs, file paths,
  sha256 hashes of texts, counts and categorical labels, plus two kinds of text:
  * 120 model-written paraphrases of qualifying AIDev review comments: 31 in
    `screening_natural_aidev_s9.json` (103 to 186 characters each) and 89 in
    `screening_natural_aidev_s9x.json` (79 to 181 characters; the 2 that failed a
    check are not stored). All were checked for logins, handles, e-mail addresses, URLs
    and runs of six or more words shared with the source texts; the extension's also
    for repository and owner names, pseudonymisation placeholders and model
    identifiers;
  * the URLs of the repositories of stage S9 in `third_party_downloads.json`: 36 for
    the first sample and 57 for the extension, 63 distinct. The same 3 of them are in
    both lists and were never fetched: the proxy refused them (status `clone_failed`).

  No verbatim comment, pull-request, issue or session text is stored (decision log
  D47, D50, D63).
* The natural PR-review index (`data/manifests/natural_tasks_index.json`): per family,
  ids, commit SHAs, licence identifiers, sha256 hashes of the task files, counts and
  the S10 and S11 outcomes, with no thread text, login, repository URL or repository
  file path; its only URLs are those of the dataset and its licence.
  The S10 download records in `third_party_downloads.json` give the bytes fetched per
  repository id (`aidev-v5-s10-repo-fetches`) and, per grading image, the number of
  wheels and their bytes (`pypi-natural-s10-wheelhouses`).
* The natural recipe's 15 prompt templates (`experiments/prompts/natural/`, D64) and its
  phase-end log (`data/manifests/natural_phase_ends.jsonl`: per family and phase, ids,
  file hashes and freeze times).
* Not stored: base snapshots of the source repositories (rebuilt from the pinned
  public commit with `tracecontract snapshot`), raw unsanitised transcripts, the fresh
  attempts' transcripts and workspaces, any gated or third-party conversation data, and
  the AIDev files, the fetched repositories and the pseudonymised texts the S9 judges
  read (all outside the repository). The natural PR-review tasks themselves
  (pseudonymised threads, base snapshots, contracts and their mappings, generated
  verifiers, candidate patches, B1 overlays, labels, audit records, S10 records, the
  fetch log and the wheel lists) and the raw results, logs and report of
  `natural-pr-v1` are under `data/natural/`, which git ignores (§17.4); the natural
  agents' workspaces and private run records are outside the repository (D64). No file
  with code of a natural repository is in git (`THIRD_PARTY_LICENSES/README.md`).

## Known biases and limitations

* By the study's procedure, every model-generated artifact comes from the same model
  family; for several roles no record holds the model's identifier, so this cannot be
  checked from the release (the paper's table of roles, `tab:roles`; D80). This covers
  the scenarios and reference contracts that define the labels, agent sessions,
  contracts, tests, attacks, alternatives, near misses, reference checks, label
  proposals, construction checks and requirement mappings, and also the fresh attempts,
  the independent labelers, the S9 judges and every agent of the natural recipe. It can
  correlate errors across conditions and with the label proposals.
* The fresh attempts add candidates, not tasks: they reuse the four controlled families
  and their frozen verifiers, and the stratum was specified after the construction
  pilot's results were known (protocol v0.7, §15.4, was hashed on 2026-11-21, D48;
  `pilot-v0.3.3` ran on 2026-11-18). With the correction in the instruction, every
  analysed `final` attempt solved its task (19 of 19 for configuration A and 20 of 20
  for B; D61): these tasks are not hard.
* The accepted natural tasks are biased toward small repositories with plain test
  setups (D59): S10 rejected, among others, families whose tests need tooling outside
  the workspace, a generated version module or a submodule, and families whose closure
  did not resolve or was too large. With six tasks, each family is reported as a case
  study, with no pooled rate (§19.6, §20.3).
* In the natural arm the reference solution is the addressing commit, not an oracle. At
  the first audit it failed 9 of the 12 audited verifiers, in every family but NP-04,
  and several of audit:v1's revisers relaxed checks that it failed; where a natural
  reference and its contract disagree, the audit settles the question for the reference
  (D70). These construction facts are model agents' observations, not reviewed by a
  person. Two families (NP-03, NP-19) have no second labeling, and 4 of the 36 held-out
  candidates are ambiguous under D19 (D75, D76).
* Protocol §15.6 states that the natural pull requests and their repositories predate
  the generators' training data, so public merged fixes may be memorised; with no model
  named, this cannot be checked (D80).
* In two of the four controlled sessions (CS-02, CS-03), the agent's pre-correction
  state passes the reference checks and the regression norm, so rule D19 labels it
  valid: the agent had already done most of what the correction asked. For CS-03
  the independent check finds divergences on non-ASCII all-caps input only (Turkish
  dotted İ, circled capitals) and disputes the label. The state before a scripted
  correction is therefore not automatically a negative.
* Scenarios were designed by the study's AI agent to contain corrections; in the
  controlled tasks and the fresh attempts, natural correction frequency and content are
  not represented.
* Base snapshots may be approximate (e.g. generated build artefacts such as
  hatch-vcs `_version.py`); approximations are listed in each `snapshot.json`. The
  leakage check recorded there was vacuous as called (decision log D47). Each base is
  instead checked against its own session (`tracecontract reconstruction-check`,
  records in `tasks/*/reconstruction_check.json`): all four pass, and CS-01 lists what
  its session cannot attest (a test file a script rewrote before its first edit, and
  three of the four lines of `_version.py`).
