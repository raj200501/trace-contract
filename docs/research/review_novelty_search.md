2. **Six works not in the brief should be cited**, because each covers one component more closely than some rows the brief already has:
   - **SWE-WhatIf** (arXiv 2611.21095, v1 2026-11-16; ARR October 2026 submission). It builds, from recorded SWE-chat/SWE-Together sessions, an "intent model" whose criteria record the user's accept/reject reasons with session evidence. Its adaptation test replays each session with an agent told to *repeat the actions the user pushed back on* versus one told to avoid them. This is the nearest published use of user-rejected behaviour as the negative condition in an evaluation built from recorded coding sessions. It is LLM-judged and validates a user simulator, not a verifier. It weakens the brief's §3.2 "Session-native negatives" bullet as worded.
   - **Agentic Auto-Rubrics (AAR)** (ICLR 2027 submission, OpenReview `bbOKndWGRf`, public 2026-10-03; abstract only, PDF not reachable). It compiles "reaction-masked" multi-turn coding sessions into "active requirements" and atomic rubrics with evidence types and code locations, then judges with an agentic verifier. It reports that baseline verifiers degrade with session length. It is closest to (d) plus "verifier built from a correction-aware contract". It must be read in full before submission.
   - **SWE-Gate** (2609.04167, v1 2026-09-03) and **SWE-Shield** (2604.05955, v1 2026-04-07). Both derive later-stated requirements from real pull-request review comments and measure how often functional tests accept patches that violate them. SWE-Gate reports 221 of 644 functional passes (34.3%) violating the review constraint. SWE-Shield's tests "substantially overestimate" quality, and its LLM verifier is checked against two experts on 318 agent patches (κ 0.7934). These are measurement analogues of (a), next to PersonaCodeBench's 20.5%, with a real source for the later requirement but no sessions.
   - **Co-Design Bench** (2610.35138, v1 2026-10-26). 273 tasks from 26,314 real user coding sessions, with expert-authored hidden criteria and an LLM judge-then-refute verifier. It is session-derived task construction with human-authored criteria. It uses reformulations and rollbacks only to rank requests, and "do[es] not simulate further user feedback".
   - **Conv-to-Bench** (2605.26440, v1 dated 2026-04-07). Real LMSYS/WildChat coding dialogues become requirement checklists whose items are tagged by origin (synthesized instruction vs specific feedback turns). ## 3. Notes on the six works that matter most

### 3.1 SWE-WhatIf (arXiv 2611.21095): closest new item for (b) and (d)

- **What it builds.** §1: "Instead of a script of the recorded replies, SWE-WhatIf extracts an intent model: the outcomes or information the user wanted (intents), the criteria by which they accepted or rejected the agent’s work, and the conditions under which each intent was raised or dropped."
  - Intent models are LLM-built by draft, review and revise agents (Claude Code on Claude Opus 5.5, App. A.1).
  - The drafting steps include "(3) for each criterion, record the evidence in the session and what the simulated user could observe in a replay to judge it". This is a correction-aware, evidence-grounded contract in all but name (INFERENCE).
  - For refinements, App. A.1 says "keep one intent and write its criteria to reflect the user’s final requirements".
- **Data.** §3.1: "Based on these requirements, we use 65 of the 109 sessions released by SWE-Together (Wu et al., 2026b) and 24 sessions from a newer release of SWE-chat (Baumann et al., 2026), for 89 tasks in all." Selection *requires* at least one pushed-back agent action.
- **The pushed-back-action contrast (the (b)-like part).**
  - §3: "However, the session reveals agent actions that the user pushed back on (e.g., a change that was later undone), and if the agent had avoided such an action, the user would not have needed to push back."
  - Same paragraph: "Based on this, we replay each session with an agent that repeats these actions and one that proactively avoids them, where a faithful simulator should produce replays with the latter agent that achieve higher burden-adjusted success."
  - Pushed-back actions are identified by an LLM (GPT-5.6 Terra), which also writes both policies' instructions (§3.2).
- **Scoring.** §2.4: "To judge success, we adapt the goal-based judging used in SWE-Together (Wu et al., 2026b): an LLM writes a list of goals for each task from the recorded session alone, and an LLM judge marks each goal as met or not met from the replay’s final state (i.e., repository changes and the agent’s messages)."
- **Result.** §3.3: "With the two versions of SWE-WhatIf, the proactive policy won 52 tasks and lost 23 with the style profile, and won 50 and lost 27 without." The win rate is 66.3 (p = .001, sign test).
- **Human involvement.** The 16-user study rates simulator fidelity and agent rankings. One author labelled simulator errors on 100 replays (κ 0.652 with Claude Sonnet 5.5). There are no human labels of candidate correctness.
- **Artifacts.** Ethics: "We do not release an artifact package containing the source sessions, code, intent models, style profiles, goals, or simulated replays."
- **Relation to D25** (INFERENCE):
  - It uses user-rejected behaviour as the negative condition, from real recorded sessions. But that behaviour is *re-enacted by a new agent told to repeat it*, not the recorded pre-correction state.
  - The object under test is the user simulator plus an LLM goal judge, not a verifier.
  - There is no initial-only vs correction-aware verifier contrast, no executable tests, no held-out labelled pool and no human candidate labels.
  - It is the published counterpart of the SF Data V8 intuition at simulator level, and its existence weakens the brief's absolute wording in §3.2 (see §5).

### 3.2 Agentic Auto-Rubrics (AAR; OpenReview `bbOKndWGRf`, ICLR 2027 submission): abstract only

- Abstract: "In multi-turn sessions, user requirements constantly change and replace earlier requests, while user reactions can unintentionally reveal task outcome and bias evaluation. We introduce $\textbf{Agentic Auto-Rubrics (AAR)}$, a framework that compiles a multi-turn interaction into a verifiable specification of what the agent is responsible for."
- Abstract: "Given reaction-masked user turns, AAR constructs the active requirements and compiles them into fine-grained atomic rubrics, which specify explicit evidence types and codebase locations."
- Abstract: "While baseline verifiers degrade as sessions lengthen, AAR maintains stable accuracy across session lengths and five judge models, showing that compiling evolving interactions into verifiable specifications enables robust evaluation of coding agents."
- **Could not verify:**
  - which benchmarks are used, or whether the sessions are real;
  - what ground truth defines "accuracy" (human or LLM labels);
  - whether any condition drops later turns (an initial-only analogue), or whether superseded-requirement violations are scored.
  - The PDF (`/pdf/4e89b9df…`), the forum and the attachment endpoints all returned the OpenReview challenge (HTTP 403). No arXiv version was found by title search.
- **Relation to D25** (INFERENCE): a correction-aware contract compiled from multi-turn coding sessions and used to build a verifier. That is exactly what D25 already concedes is not new. It is LLM-judged, not executable. Its "accuracy across session lengths" is a verifier-fidelity measurement on multi-turn coding sessions. If its ground truth is human and its pool contains outputs that satisfy superseded requests, it would come close to (a) and (c). This is the single highest-priority unread item.

### 3.3 SWE-Gate (2609.04167) and SWE-Shield (2604.05955): later-stated requirements from PR review

- **SWE-Gate source and design.**
  - §2 (Constraint Extraction): constraints come from "suggestions explicitly stated in review comments" of merged PRs. They are then transferred into other repositories by an agent, so instances are synthesized and are not the original PRs.
  - Abstract: "Each instance provides separate functional and constraint tests, together with non-compliant and gold patches, enabling explicit separation between issue resolution capability and review constraint compliance."
  - The non-compliant patch is agent-constructed (§2, Instance Synthesis): "Second, it creates constraint_test.patch, a natural functional but non-compliant non-compliant.patch, and a compliant gold.patch."
- **SWE-Gate measurement (a)** (RQ1): "Across the four models, 644 generated patches pass the functional tests, but only 423 pass both test suites. SWE-Gate therefore identifies 221 hidden failures, corresponding to 34.3% of all functional successes."
  - The "Hidden Failure Rate" is the share of functional-test passes that violate the later-stated (review) requirement. It ranges from 29.5% to 53.6% by model.
  - A −C/+C ablation shows the constraint text matters to *agents*.
  - There are no human candidate labels; quality assurance includes manual inspection of the instances.
- **SWE-Shield** (abstract): "Experiments with state-of-the-art agents show that test-based correctness substantially overestimates patch quality: fewer than half of resolved issues are fully design-satisfying, design violations are widespread, and functional correctness exhibits negligible statistical association with design satisfaction."
  - Its verifier is an LLM ensemble. §4.2: "The comparison yields a consistency rate of 80.8% between human annotations and the verifier judgments, with a Cohen’s kappa of 0.7934, indicating substantial agreement." That is 318 sampled agent patches with two experts.
- **Relation to D25** (INFERENCE):
  - Both measure "tests built without a later requirement accept outputs that violate it". The later requirement has a real human source (maintainer review), the analogue of a correction.
  - Differences from D25: no sessions; constructed tasks or constraints; no generated initial-only vs correction-aware verifier pair; no pre-correction (pre-review) state used as a negative; no FR on valid alternatives (SWE-Gate's gold patch is a positive control only).
  - Precedent worth noting: AIDev-pop review comments (brief §4.3) would give D25 a natural pre-review state, and these two benchmarks show the PR-review framing is already in use.

### 3.4 Co-Design Bench (2610.35138): session-derived tasks with expert criteria

- Abstract: "We introduce Co-Design Bench, a reference-free benchmark of 273 tasks curated from 37,463 deduplicated queries across 26,314 real user coding sessions." Abstract: "The tasks pair normalized requests and runnable pre-edit applications with 2,331 hidden expert-authored acceptance criteria."
- §3.2: "Remaining candidates are ranked by structural difficulty, verifiability, and historical failure signals such as reformulations and rollbacks, then consolidated into bounded session intervals." §3.2: "The resulting tasks preserve session-derived revision goals but evaluate a fixed request; they do not simulate further user feedback during execution."
- The verifier is an LLM judge with a separate LLM refuter. App.: "Two frontend experts checked the judge model’s rubric scores for a total of 200 task–model outputs." I did not find agreement numbers in the text I extracted.
- **Relation to D25** (INFERENCE): session → task with human-authored, interval-consolidated criteria, which is a human-made correction-aware contract. Rollbacks are a selection signal, not negatives. There is no FA/FR on a labelled pool, no initial-only arm and no executable tests.

### 3.5 Conv-to-Bench (2605.26440): origin-tagged checklists from real dialogues

- §3.3: "To ensure full traceability, the model is instructed to tag each requirement with its origin, distinguishing between criteria derived from the synthesized instruction and those stemming from specific feedback turns."
- §4.1: 387 instruction–checklist pairs from LMSYS-Chat-1M and WildChat. "This dataset comprises a total of 2,851 checklist items, with 2,595 requirements derived directly from instructions and 256 extracted from user feedback, naturally mirroring the scarcity of explicit feedback."
- Its "Instructions-Only" arm is **not** initial-only. §4.4: "As detailed in Section 3.2, this instruction represents the consolidated user intent extracted from the entire conversational history, rather than just the initial message, integrating the primary request with all subsequent task-related refinements."
- §5.2: "The results indicate that the inclusion of feedback does not yield consistent improvements in evaluative integrity." Evaluative integrity is measured as rank correlation with BigCodeBench, not as candidate-level FA.
- §4.3 and §5.1: judge vs human-verified labels on a stratified sample of 488 points per evaluator (§4.3). §5.1 reports κ of 0.705 (Gemini) and 0.649 (GPT-5-Mini), which "indicate a substantial level of agreement with human experts"; DeepSeek has 0.464, with negative-class F1 0.574.
- **Relation to D25** (INFERENCE): an earlier precedent for (d), with per-item provenance from conversation turns, and for reporting the LLM-vs-human label gap. It uses chat, not agent sessions, an LLM checklist judge and no executable verifiers.

### 3.6 Lower-overlap items worth one line in the brief

- **SWEPatchTest** (abstract): "By replaying each suite on the buggy and patched codebases, \benchmark jointly measures issue reproduction, acceptance of correct patches, and rejection of incorrect patches." The pool is 82,579 candidate patches from coding-agent trajectories, labelled by the source benchmarks' tests. Best JVR is 9.21%.
- **VerifierContractBench** (OpenReview abstract): "Each episode starts from a frozen multimodal verifier, exposes 102 expert-labeled web-agent trajectories, permits six edit–evaluate–rollback rounds, and freezes the final incumbent before evaluation on 492 task-disjoint trajectories." Its NUCR counts unsafe trajectories that the edited verifier newly approves. This is the audit-arm analogue of D25's C3→C4 FA check, outside coding.
- **Benchmark Factory** (abstract): "Engineering raters scored a 5% sample 2.3 for task quality and 2.6 for grader verdicts on a 1-to-3 scale."
- **IntentFlux** (abstract): intent drift is "the failure mode in which superseded parts of the user's intent continue to influence the final answer or tool action". The benchmark "converts verifiable tasks into dialogues with controlled intent changes while preserving their original graders". That makes it agent-side.
- **WildFeedback** (abstract): "The user feedback is then used to create examples of preferred and dispreferred responses according to users' preference." It treats the response a user rejected in-session as a negative, for training rather than verifier audit (2024, ACL 2026).

## 6. Limitations of this search

- **OpenReview full texts are not readable here.** The search API works, but forum, PDF and attachment endpoints return the browser challenge, so AAR, the SessionFarmer ICLR revision, VibeSWEBench, VerifierContractBench and the other OpenReview-only items are abstract-level. OpenReview search is keyword-ranked and noisy; relevant submissions with unusual wording may have been missed.
- **arXiv listings:** cs.SE was read in full for Sep–Nov 2026. cs.AI and cs.CL were only keyword-filtered by title, so papers whose titles avoid coding, session, verifier and feedback vocabulary could be missed. arXiv's abstract search does not behave as a strict phrase search, so recall depends on wording.
- **Semantic Scholar** coverage of November 2026 is thin by nature: SessionFarmer and SWE-WhatIf have 0 citing records, and several seeds have 0–1. The S2 web pages were not usable; the API returns the same graph.
- **Not searched:** Google Scholar, ACM DL and IEEE Xplore full text, ACL Anthology volume pages (only via WebSearch), company research blogs beyond WebSearch results, and non-English venues.
- **Read in full** only for SWE-WhatIf (main text and key appendices) and SWE-Gate. SWE-Shield, Co-Design Bench and Conv-to-Bench were read in targeted sections; everything else is abstract-level. Figures were not inspected.
- WebSearch result summaries are secondary. Every candidate reported here was re-opened on its primary record, and nothing in this note rests on a search snippet.
